# 多卡通信

本章面向已经能分析单卡计算和带宽的读者。完成后，你应能解释常见集合通信的输入输出语义，估算理想环形通信量，并说明物理拓扑为什么会改变分布式训练和推理的扩展效率。

## 学习目标与前置知识

- 区分全归约、全收集和归约分散。
- 用参与设备数、逻辑载荷和有效带宽估算理想环形通信下界。
- 识别同节点与跨节点路径中的潜在慢链路。
- 先完成[计算与带宽分析](02-compute-and-bandwidth.md)。

## 从逻辑秩到物理路径

分布式程序通常给每个参与进程一个逻辑秩（Rank）。逻辑秩会映射到 GPU、CPU 的非统一内存访问节点、网卡和物理机器。集合通信库根据这些设备建立通信路径。

常见物理层次包括：

- 同一 GPU 内的存储层次。
- 同一节点内经过 PCIe（高速串行计算机扩展总线）、交换芯片或 NVLink（英伟达高速互联）的 GPU 间路径。
- 跨节点经过网络接口、交换网络和远程直接内存访问（Remote Direct Memory Access，RDMA）的路径。
- InfiniBand（无限带宽网络）或以太网等网络技术；具体能力取决于网卡、交换机、协议和配置。

通信性能由端到端路径决定。即使大部分 GPU 之间有高速连接，只要算法频繁经过较慢或拥塞的链路，整体时间仍可能受该路径限制。调度器需要理解拓扑，而不能只统计空闲 GPU 数量。

## 三种集合通信

NVIDIA Collective Communications Library（英伟达集合通信库，NCCL）的[集合通信文档](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html)定义了以下语义：

| 集合通信 | 每个秩的输入 | 每个秩的输出 | 常见用途 |
| --- | --- | --- | --- |
| All-Reduce（全归约） | 相同大小的完整数组 | 所有秩输入逐元素归约后的完整数组 | 数据并行梯度同步 |
| All-Gather（全收集） | 一个分片 | 按秩拼接后的完整数组 | 收集参数或激活分片 |
| Reduce-Scatter（归约分散） | 相同大小的完整数组 | 归约结果中的一个分片 | 分片梯度或状态 |

NCCL 文档还指出，Reduce-Scatter 后接 All-Gather 在数据语义上等价于 All-Reduce。实际实现可能选择环形、树形或其他算法，并依据消息大小和拓扑调整，因此课程的环形公式不能预测 NCCL 的真实选择。

## 理想环形通信量

设参与设备数为 `N`，逻辑完整载荷为 `M` 字节。课程使用以下定义：

- 对 All-Reduce，`M` 是每个秩输入和最终输出的完整数组大小。
- 对 All-Gather，`M` 是每个秩最终得到的完整数组大小，每个秩初始持有 `M/N`。
- 对 Reduce-Scatter，`M` 是每个秩输入的完整数组大小，每个秩最终保留 `M/N`。

在均衡环形模型中，每个设备的理想发送流量为：

- All-Reduce：`2 × (N - 1) ÷ N × M`。
- All-Gather：`(N - 1) ÷ N × M`。
- Reduce-Scatter：`(N - 1) ÷ N × M`。

如果把用户提供的端到端有效带宽记为 `B`，只考虑带宽的理想时间为 `流量 ÷ B`。模型没有加入每一步固定延迟、协议开销、链路共享、收发方向差异或拓扑不均衡。

## 运行集合通信估算实验

运行默认教学配置：

```bash
python3 examples/collective_estimator.py
```

配置使用 8 个设备、`4 GiB` 逻辑载荷和假设的 `400 GB/s` 每设备有效带宽。结果应为：

| 集合通信 | 每设备理想流量 | 仅带宽时间下界 |
| --- | ---: | ---: |
| All-Reduce（全归约） | `7 GiB` | 约 `18.79 ms` |
| All-Gather（全收集） | `3.5 GiB` | 约 `9.40 ms` |
| Reduce-Scatter（归约分散） | `3.5 GiB` | 约 `9.40 ms` |

脚本中的载荷使用二进制 `GiB`，带宽使用十进制 `GB/s`，因此不能直接把数值相除而忽略单位换算。

将有效带宽改为 `50 GB/s`，模拟路径中出现更慢链路：

```bash
python3 examples/collective_estimator.py \
  --collective all-reduce --bandwidth-gb-s 50
```

理想时间下界应增至约 `150.32 ms`。这只说明在相同流量模型下，带宽下降会提高时间下界；它不代表任何具体 PCIe、NVLink、InfiniBand 或以太网配置。

将设备数改为 2 和 16，观察环形因子：

```bash
python3 examples/collective_estimator.py \
  --collective all-reduce --devices 2

python3 examples/collective_estimator.py \
  --collective all-reduce --devices 16
```

设备增加时，每设备带宽流量因子逐渐接近 `2`，但真实扩展效率还会受到步骤数、固定延迟、链路并发和拓扑影响。

## 从公式走向多卡测量

真实实验至少记录以下条件：

- GPU 型号、数量与逻辑秩映射。
- 节点数量、CPU 非统一内存访问关系、网卡和交换拓扑。
- CUDA（统一计算设备架构）、NCCL、驱动及框架版本。
- 集合通信类型、数据类型、消息大小和预热次数。
- 平均、P50、P95 延迟，以及由真实载荷计算的有效带宽。
- 是否与计算重叠、是否存在其他作业共享链路。

测量结果应与单卡无通信基线对照。只报告“多卡每秒处理量”无法区分通信、负载不均和计算效率变化。

## 验收标准

- 能说明三种集合通信的输入和输出。
- 能复算八卡 `4 GiB` All-Reduce 的 `7 GiB` 每卡流量与 `18.79 ms` 下界。
- 能解释 `GiB` 与 `GB/s` 的单位差异。
- 能画出一个跨节点通信路径，并标出潜在慢链路。
- 能列出至少五项环形模型没有覆盖的真实开销。
