# GPU 资源暴露与隔离

本章面向需要把推理或训练任务放进共享集群的工程师。完成后，你应能沿着硬件、驱动、Device Plugin（设备插件）、节点和 Pod（容器工作负载单元）解释 GPU（图形处理器）如何成为可调度资源，并区分“资源记账”“设备可见”和“性能隔离”。

## 学习目标与前置知识

- 画出 GPU 从节点硬件到工作负载资源请求的暴露链路。
- 解释 Kubernetes（容器编排系统）对 GPU 请求的基本约束。
- 区分整卡、MIG（Multi-Instance GPU，多实例 GPU）和纯软件共享的隔离边界。
- 识别调度成功不等于性能、显存和故障完全隔离。
- 先完成[容器与部署](../02-distributed-cloud-native/01-containers-and-deployment.md)和[GPU 架构与存储](../03-gpu-interconnect/01-gpu-architecture.md)。

## 从硬件到可调度资源

以 Kubernetes 为例，资源暴露通常经过以下链路：

`GPU 硬件 → 内核驱动与用户态运行时 → 厂商设备插件 → 节点可分配资源 → Pod 资源请求 → 容器内设备`

各层职责不同：

| 层次 | 主要职责 | 不能单独保证什么 |
| --- | --- | --- |
| 驱动与运行时 | 让操作系统和计算库访问设备 | 不决定队列公平性 |
| 设备插件 | 发现设备、向节点代理注册扩展资源并参与分配 | 不替代集群队列和租户配额 |
| 调度器 | 根据资源请求和放置约束选择节点 | 不预测某个模型的真实吞吐 |
| 容器运行时 | 把获分配的设备暴露给容器 | 不天然消除共享硬件上的性能干扰 |
| 作业或服务控制器 | 管理副本、失败重建和生命周期 | 不自动解决容量不足 |

Kubernetes 官方的 [GPU 调度说明](https://kubernetes.io/docs/tasks/manage-gpus/scheduling-gpus/)要求先安装厂商驱动和对应设备插件。插件注册后，GPU 通常以 `nvidia.com/gpu` 这类扩展资源名出现。官方文档还说明：GPU 资源可以只写在 `limits`（上限）中；若同时写 `requests`（请求）和 `limits`，两者必须相等。实际资源名和安装方式取决于设备厂商及插件版本，应以目标集群的节点状态和官方文档为准。

下面的片段只展示资源字段，不是可直接用于生产的完整部署清单：

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

这个数字表达调度器要记账的扩展资源数量。它没有描述模型显存峰值、输入长度、并发、设备代际或跨卡通信，因此“成功调度一张卡”不能推出“服务一定满足延迟目标”。

## 三种常见隔离边界

### 整卡分配

一个工作负载获得完整物理 GPU，资源模型和故障边界最容易解释。代价是小负载可能无法充分利用显存或计算单元。即使整卡独占，主机 CPU、内存、PCIe（外围组件高速互连）和网络仍可能共享。

### MIG 多实例 GPU

NVIDIA 的 [MIG 用户指南](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/introduction.html)说明，MIG 可把受支持的 GPU 划分为多个具有隔离资源的实例。是否支持、能创建哪些配置、需要什么驱动和软件版本，都与具体硬件及版本有关，不能把某一型号的配置泛化到所有 GPU。

MIG 提供的是硬件支持的分区能力，但平台仍需处理实例发现、资源命名、队列、监控和生命周期。课程后续把每个可分配单元简化为整数槽位，不模拟 MIG 配置。

### 纯软件共享

多个进程可以通过时间复用或运行时机制共享设备，但具体行为取决于实现。仅把多个进程放到同一 GPU，不代表它们获得固定比例的计算、显存带宽或尾延迟。若采用这类方案，应实际测量显存越界、争用和故障传播，而不是从配置名称推断隔离强度。

## 调度、可见性与隔离要分开验证

排查共享 GPU 问题时，依次回答三个问题：

1. **调度层：**节点是否报告了期望的可分配资源，工作负载请求是否匹配？
2. **运行层：**容器内是否能看到被分配的设备，驱动和计算库是否兼容？
3. **服务层：**目标模型在规定输入、并发和精度下是否满足显存、吞吐和尾延迟要求？

第一步成功只证明资源记账和放置路径基本可用。第三步仍需负载测试；测试方法见[基准测试与服务目标](../07-inference-infra/03-benchmark-and-slo.md)。

## 无 GPU 环境的配额实验

仓库提供一个只依赖 Python 标准库的教学模拟器。它把每个 GPU 当成相同的整数槽位，用于观察资源记账，不连接 Kubernetes，也不执行模型：

```bash
python3 examples/gpu_scheduler_simulator.py examples/gpu_jobs.csv \
  --policy fifo \
  --quota team-a=4 \
  --quota team-b=6 \
  --quota team-c=2
```

检查输出中的 `schedule`（调度结果）和 `allocation`（资源分配）：

- 六个作业都应完成，`unschedulable`（不可调度）应为 `0`。
- `team-a` 的 `j1` 占用 4 个槽位时，`j3` 即使只需要 2 个槽位，也要等 `j1` 结束后才能启动。
- 这只验证模拟器里的并发配额约束，不证明真实集群已经隔离显存、带宽或故障。

再构造一个需要 5 个 GPU 且要求同一节点的作业。在默认“每节点 4 个 GPU”条件下，即使集群总计有 8 个 GPU，它也应被判为不可调度。这说明总量足够不等于单节点形状可满足。

## 验收标准

- 能画出从 GPU 硬件到容器可见设备的完整链路，并说明每层职责。
- 能解释 Kubernetes GPU 的扩展资源、设备插件以及请求与上限的约束。
- 能比较整卡、MIG 和纯软件共享的隔离边界，不把资源请求当成性能保证。
- 能运行模拟器并用 `j1`、`j3` 解释租户并发配额如何阻塞作业。
- 能列出真实集群仍需核验的硬件型号、驱动、插件、资源名和负载条件。
