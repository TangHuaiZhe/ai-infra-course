# 弹性与故障

本章面向需要让 GPU（图形处理器）工作负载应对节点不可用和容量变化的工程师。完成后，你应能把“自动扩缩容”拆成可验证的控制环，并为节点故障写出包含检测、隔离、重建、流量恢复和容量回补的时间线。

## 学习目标与前置知识

- 区分工作负载扩缩容、节点扩缩容和故障恢复。
- 解释故障域、容量余量和拓扑约束如何共同影响恢复。
- 用模拟器观察节点不可放置如何放大排队和资源碎片。
- 写出不掩盖数据丢失、重试和冷启动代价的故障验收方案。
- 先完成[队列、配额与拓扑](02-queues-and-topology.md)和[分布式推理服务](../07-inference-infra/04-distributed-serving.md)。

## 三个控制环不要混为一谈

### 工作负载扩缩容

它根据请求量、队列深度或其他信号调整服务副本或作业并行度。增加副本只会产生更多资源请求；如果集群没有可放置的 GPU，新副本仍会等待。

### 节点扩缩容

它根据不可调度工作负载和节点利用情况增加或减少机器。Kubernetes 的 [Node Autoscaling（节点自动扩缩容）说明](https://kubernetes.io/docs/concepts/cluster-administration/node-autoscaling/)指出，扩容要受云服务商集成、节点池配置和容量限制等条件约束。即使控制器决定扩容，实例供应、启动、驱动和设备插件就绪仍需要时间，且外部容量不一定可得。

### 故障恢复

它先检测异常，再阻止新流量或新放置，随后重建工作负载并验证服务。节点自动扩缩容可以补容量，但不会替代请求重试、检查点、一致性和服务就绪判断。

这三个控制环的信号、时间尺度和失败方式不同。仅看到副本数回升，不能证明请求已经恢复或模型状态没有丢失。

## 从节点故障到服务恢复

一个可审计的恢复路径至少包含：

1. **检测：**节点心跳、设备错误或服务探针发现异常。
2. **隔离：**停止向异常实例发送新请求，并阻止新工作负载放到不可用节点。
3. **判定：**区分短暂抖动、进程故障、设备故障和整机故障，避免无界重试。
4. **重建：**在其他故障域重新放置副本；有状态训练任务从经过验证的检查点恢复。
5. **预热：**加载模型、建立缓存或完成健康检查，未就绪副本不应接收正式流量。
6. **回流：**逐步恢复流量，观察错误率、尾延迟和队列，而不是一次性切满。
7. **回补：**补足冗余容量，并确认新节点的驱动、设备插件和监控正常。

Kubernetes 使用 taint（污点）和 toleration（容忍）等机制影响 Pod（容器工作负载单元）的放置与驱逐；官方[污点与容忍说明](https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/)给出了语义。具体节点故障判定和驱逐时间与集群配置及版本有关，本章不假定固定秒数。

## 容量余量与故障域

把副本分散到多个故障域，只有在其他域存在可用容量时才能提高恢复能力。规划时至少计算：

- 正常峰值负载下需要多少副本；
- 损失一个节点、机架或可用区后还剩多少可服务容量；
- 模型加载和缓存预热期间的临时双份资源；
- 拓扑“必须满足”约束是否阻止备用位置；
- 在线预留容量能否被离线作业借用，以及故障时如何回收。

容量余量不是越多越好：它提高恢复空间，也增加空闲成本。合理目标应来自服务目标、故障概率、恢复时间和业务损失，而不是固定百分比。

## 注入一个节点不可放置窗口

运行以下教学模拟：

```bash
python3 examples/gpu_scheduler_simulator.py examples/gpu_jobs.csv \
  --policy fifo \
  --quota team-a=4 \
  --quota team-b=6 \
  --quota team-c=2 \
  --outage node-1:250:700
```

`--outage`（不可用窗口）让 `node-1` 在时间 `250` 到 `700` 之间拒绝新放置。结果应为：

| 指标 | 无故障 FIFO | 注入不可用窗口 |
| --- | ---: | ---: |
| 平均等待时间 | 125.00 ms | 175.00 ms |
| P95 等待时间 | 400 ms | 550 ms |
| `j4` 启动时间 | 500 ms | 650 ms |
| `j4` 等待时间 | 400 ms | 550 ms |

在故障场景中，`j3` 和 `j6` 分别占用 `node-0` 的两个槽位，`j4` 要求同节点 4 个槽位，因此必须等到时间 `650`。这展示了容量损失与资源碎片如何共同放大排队。

模拟器的边界必须同时记录：

- 不可用窗口只阻止**新放置**，不会中断已经运行的作业。
- 程序预先知道恢复时间，未模拟心跳、检测延迟或误判。
- 没有请求、容器、模型加载、检查点、重试、抢占或节点扩容。
- 所有 GPU 被视为同质整数槽位，没有真实硬件与网络拓扑成本。

因此，这个结果只能验收调度推理，不能作为真实恢复时间目标或生产容量结论。

## 真实环境的故障实验记录

在获准的测试环境中进行故障注入时，记录统一时间原点下的事件：

| 时间 | 事件 | 证据 |
| --- | --- | --- |
| T0 | 注入节点或进程故障 | 操作记录与目标标识 |
| T1 | 监控发现异常 | 告警、事件或指标 |
| T2 | 实例停止接收新流量 | 路由状态与请求记录 |
| T3 | 替代副本被调度 | 调度事件与目标节点 |
| T4 | 模型加载并通过就绪检查 | 启动日志与探针状态 |
| T5 | 流量恢复且指标稳定 | 错误率、尾延迟和吞吐 |

至少分别计算：检测时间 `T1 - T0`、隔离时间 `T2 - T0`、重新就绪时间 `T4 - T0` 和服务恢复时间 `T5 - T0`。同时报告失败请求数、重试数、丢失或重复任务、排队峰值和实验期间的有效容量。

## 验收标准

- 能区分工作负载扩缩容、节点扩缩容和故障恢复的输入、动作与完成信号。
- 能复现不可用窗口实验的 `175 ms` 平均等待、`550 ms` P95 等待和 `j4` 的 `650 ms` 启动时间。
- 能解释为何“节点数恢复”不等于“服务已恢复”。
- 能为一个在线推理服务写出 T0 到 T5 的故障时间线和证据字段。
- 能明确列出模拟器没有覆盖的至少五项生产条件。
