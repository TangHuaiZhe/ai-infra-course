# 队列、配额与拓扑

本章面向需要在共享 GPU（图形处理器）集群上同时承载训练、离线推理和在线服务的工程师。完成后，你应能解释一个工作负载为何“总资源够却仍在等待”，并用排队、配额、整组分配和拓扑约束分析利用率与服务优先级的取舍。

## 学习目标与前置知识

- 区分队列顺序、租户配额、节点可行性和拓扑约束。
- 解释 all-or-nothing（全有或全无）准入与 gang scheduling（整组调度）的目的。
- 比较 FIFO（First In, First Out，先到先服务）与 Priority（优先级）策略。
- 识别队首阻塞、资源碎片和抢占的副作用。
- 先完成[GPU 资源暴露与隔离](01-gpu-resources.md)。

## 调度不是简单减法

集群有 8 个空闲 GPU，不代表任何申请 8 个 GPU 的作业都能立即运行。调度至少要同时满足：

`队列允许准入 ∧ 租户配额足够 ∧ 节点资源形状可行 ∧ 拓扑约束满足`

例如，两个节点各空闲 4 个 GPU：

- 可把一个允许跨节点的 8 卡作业放到两个节点；
- 不能满足“8 卡必须在同一节点”的作业；
- 若租户并发配额只有 4 卡，即使物理资源空闲，也不能准入 8 卡作业；
- 若 4 卡节点只剩分散的 `2 + 2` 个空闲槽位，也不能放置要求同节点的 4 卡作业。

因此，应把“逻辑准入”和“物理放置”分成两次判断。Kueue（Kubernetes 原生作业排队系统）的[准入说明](https://kueue.sigs.k8s.io/docs/concepts/admission/)也把逻辑资源配额与可选的物理拓扑可行性区分开来。

## 五个核心机制

### 队列顺序

FIFO 容易解释，但大作业可能造成 head-of-line blocking（队首阻塞）：排在前面的作业暂时放不下，后面能放下的小作业是否可以越过它，需要明确策略。允许越过能提高利用率，却可能让大作业持续等待。

优先级可以让在线恢复任务或关键作业更早获得资源，但若没有等待时间修正、配额或老化机制，低优先级工作负载可能饥饿。优先级是业务决策，不等同于作业更“重要”的客观事实。

### 配额

配额限制租户或资源池可同时占用的资源。它能防止单个团队吞掉全部容量，但过于静态的配额会让空闲资源无法借用。设计时应明确：

- 配额是硬上限、保障量还是可借用份额；
- 借用资源何时归还；
- 统计的是 GPU 数量、特定型号，还是带显存档位的资源类别；
- 在线服务预留容量是否与批处理作业共享。

Kueue 的 [ClusterQueue（集群队列）概念](https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/)提供了配额和资源风味等抽象；具体字段和行为会随版本变化，部署时需核对目标版本。

### 全有或全无准入

一个需要 8 个工作进程的分布式作业，如果只启动 3 个，其余进程可能一直等待，已占用的 GPU 也无法产出。全有或全无准入要求整组资源同时满足后再启动。Kueue 对[全有或全无语义](https://kueue.sigs.k8s.io/docs/concepts/all_or_nothing/)有专门说明。

本课程模拟器把每个作业一次性分配全部 GPU，近似演示这个原则；它没有模拟 Kubernetes Pod、协调器或真实分布式启动过程。

### 拓扑约束

跨节点、跨机架或跨网络域通信的代价可能不同。Kueue 的[拓扑感知调度说明](https://kueue.sigs.k8s.io/docs/concepts/topology_aware_scheduling/)区分 required（必须满足）、preferred（尽量满足）和不指定拓扑等意图。把所有约束都设为“必须”会降低可调度性；全部放宽又可能付出通信性能代价。

模拟器的 `same_node=true` 只表示“所有槽位必须来自同一节点”。它没有表示 NUMA（非一致内存访问）、PCIe（外围组件高速互连）、NVLink（英伟达高速互连）、交换机层级或通信成本。

### 抢占

抢占可以回收低优先级工作负载的资源，但被回收的任务可能丢失进度、触发重试并增加集群抖动。采用抢占前，应明确检查点成本、最短运行时间、优雅终止窗口和重试预算。课程模拟器**不实现抢占**，所有已经启动的作业都会运行到完成。

## 对比 FIFO 与优先级

在仓库根目录运行：

```bash
python3 examples/gpu_scheduler_simulator.py examples/gpu_jobs.csv \
  --quota team-a=4 \
  --quota team-b=6 \
  --quota team-c=2
```

未显式指定 `--policy`（策略）时，程序依次输出 FIFO 和优先级两份 JSON（JavaScript 对象表示法）结果。样例是假设性负载，时间单位为毫秒，不是实际集群测量。

| 策略 | `j4` 启动时间 | `j4` 等待时间 | 平均等待时间 | P95 等待时间 |
| --- | ---: | ---: | ---: | ---: |
| FIFO | 500 | 400 | 125.00 | 400 |
| 优先级 | 400 | 300 | 108.33 | 350 |

差异发生在时间 `400`：

1. `j3` 更早到达，FIFO 先给它 2 个槽位，留下的碎片无法满足 `j4` 的同节点 4 卡要求。
2. 优先级策略先选择优先级更高的 `j4`，把完整节点分给它。
3. 该样例中优先级策略降低了两个汇总指标，但不能据此推断它在其他负载中一定更好。改变到达时间、时长、配额或拓扑，结论可能反转。

查看单一策略可以减少输出：

```bash
python3 examples/gpu_scheduler_simulator.py examples/gpu_jobs.csv \
  --policy priority \
  --quota team-a=4 \
  --quota team-b=6 \
  --quota team-c=2
```

## 设计一套可审计的策略

不要只写“高优先级先运行”。至少记录：

1. **准入单位：**单个副本、整组工作进程还是整个服务版本。
2. **资源口径：**GPU 数、型号、显存档位、CPU 和网络是否一起约束。
3. **公平边界：**租户配额、可借用份额和归还条件。
4. **拓扑意图：**必须满足、尽量满足还是不关心。
5. **阻塞处理：**是否允许后到的小作业越过暂时不可放置的大作业。
6. **抢占规则：**谁能抢占谁，以及进度损失如何计入成本。
7. **观测指标：**准入等待、不可调度原因、资源碎片、利用率和饥饿时间。

## 验收标准

- 能用“准入、配额、放置、拓扑”四步解释作业等待原因。
- 能说明全有或全无准入为何能避免部分启动长期占用资源。
- 能复现表格中的 FIFO 与优先级结果，并解释 `j4` 提前启动的原因。
- 能说明这次模拟为什么不能证明优先级策略普遍优于 FIFO。
- 能为一个在线推理与离线作业混部场景写出配额、拓扑和抢占规则。
