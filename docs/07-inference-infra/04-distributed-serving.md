# 分布式推理服务

本章面向已理解单机推理指标的读者。完成本章后，你应能区分模型路由与副本路由，解释负载均衡、缓存亲和和故障隔离之间的取舍，并用教学模拟器验证自己的判断。本章不教授某个框架的生产部署，也不提供真实 GPU 性能结论。

## 学习目标与前置知识

- 区分入口层的模型选择与服务内部的副本选择。
- 解释最短队列、前缀亲和与副本就绪状态分别解决什么问题。
- 分析副本故障如何改变缓存命中、排队和请求完成情况。
- 先完成[基准测试与服务目标](03-benchmark-and-slo.md)，并阅读[分布式服务治理](../02-distributed-cloud-native/02-distributed-services.md)和[GPU 资源暴露与隔离](../05-gpu-scheduling/01-gpu-resources.md)。

## 请求经过的两层路由

一个多模型、多副本服务至少要回答两个不同问题：

```text
客户端请求
    │
    ▼
入口层：这个 model_id 应进入哪个模型部署？
    │
    ▼
副本路由器：这个部署中的哪个副本处理请求？
    │
    ▼
模型副本：排队、预填充、解码、流式返回
```

入口层处理模型名称、版本、租户或能力之间的映射。副本路由器在同一模型部署的多个实例中选择目标。[Ray Serve LLM 的路由文档](https://docs.ray.io/en/latest/serve/llm/architecture/routing-policies.html)也明确区分了模型级入口路由与副本级请求路由。混淆两者，会让容量和故障分析落在错误层次。

## 三类路由信号

### 负载

路由器可根据副本的在途请求数、队列长度或预计完成时间分配新请求。课程模拟器使用“预计队列等待最短”作为对照策略。它是为了说明原理而设计的确定性策略，**不是 Ray Serve 的默认算法**；Ray 官方文档描述的默认路由使用两次随机抽样后选择负载较小的副本。

负载信息可能延迟，也不一定等价于剩余工作量。两个副本都有一个请求时，一个可能正在处理短解码，另一个可能正在处理长预填充。真实系统需要用实测判断哪些信号最有预测力。

### 缓存亲和

共享系统提示词或少样本示例的请求可能拥有相同前缀。把相似前缀路由到已保存对应键值缓存（KV Cache）的副本，可能减少重复计算。亲和过强也可能让某个副本排队，而其他副本空闲。

[Ray 的前缀感知路由文档](https://docs.ray.io/en/latest/serve/llm/user-guides/prefix-aware-routing.html)采用“负载较均衡时考虑前缀，负载失衡时回退到负载均衡”的思路。课程模拟器用一个简化阈值表达相同的取舍，但不复刻 Ray 的实现、前缀匹配方法或缓存回收策略。

### 就绪状态

副本启动、加载模型、发生故障或准备退出时，不应继续接收新请求。在 Kubernetes 中，`Ready` 条件表示 Pod 能够服务请求，并应进入匹配服务的负载均衡池；详见 [Pod 生命周期文档](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)。就绪检查只能说明副本是否应该接收新流量，不能自动保证已经接收的请求能够完成。

## 故障与恢复边界

设计故障处理前，先回答以下问题：

- 路由器多久能发现副本不可用？
- 已进入故障副本队列的请求会失败、完成还是重试？
- 流式响应开始后是否还能安全重试？
- 重试是否会造成重复计费、重复写入或负载放大？
- 新副本完成模型加载和预热前，何时对外宣告就绪？

在线推理请求不一定具有可安全重试的语义。客户端已经收到部分输出后，再把请求切到另一副本，可能产生不同的续写结果。课程实验只模拟“停止给不就绪副本分配新请求”，不模拟中途失败、重试或输出一致性。

## 运行路由模拟实验

实验需要 Python 3.9 或更新版本，不依赖第三方库或 GPU。输入文件包含八条带到达时间、前缀标签和基础服务时间的教学请求。服务时间和缓存节省量都是假设值。

### 比较两种策略

在仓库根目录运行以下命令：

```bash
python3 examples/routing_simulator.py examples/routing_trace.csv
```

脚本同时运行两种策略：

- `least-queue`：选择预计队列等待最短的就绪副本。
- `prefix-affinity`：如果保存了相同前缀的副本，其预计等待时间没有比最短队列多出超过 `100 ms`，则优先选择它；否则回退到最短队列。

默认配置使用两个副本，并假设缓存命中可从基础服务时间中减去 `80 ms`。你应看到以下摘要：

| 策略 | 缓存命中数 | 平均排队时间 | P95 端到端延迟 |
| --- | ---: | ---: | ---: |
| 最短队列 | 3 | 125.0 ms | 360.0 ms |
| 前缀亲和 | 4 | 122.5 ms | 340.0 ms |

这些结果只验证本次输入和模拟规则。它们不能证明前缀亲和在真实服务中一定更快。

### 注入单副本故障

让 `replica-0` 在模拟时间 `300–500 ms` 内停止接收新请求：

```bash
python3 examples/routing_simulator.py examples/routing_trace.csv \
  --failure replica-0:300:500
```

检查 `r7` 的分配结果。两种策略都应把它交给 `replica-1`，八条请求仍全部完成。此时前缀亲和策略的缓存命中数降为 `3`，说明故障转移也会改变缓存局部性。

### 模拟容量全部不可用

让两个副本在同一时间窗口停止接收新请求：

```bash
python3 examples/routing_simulator.py examples/routing_trace.csv \
  --failure replica-0:300:500 \
  --failure replica-1:300:500
```

`r7` 和 `r8` 应显示为 `rejected`，即拒绝。模拟器没有等待队列、自动扩缩容或重试，因此不会在副本恢复后重新提交它们。

### 改变亲和阈值

将允许等待的阈值改为 `0 ms`，再与 `300 ms` 对比：

```bash
python3 examples/routing_simulator.py examples/routing_trace.csv \
  --policy prefix-affinity --max-affinity-wait-ms 0

python3 examples/routing_simulator.py examples/routing_trace.csv \
  --policy prefix-affinity --max-affinity-wait-ms 300
```

阈值越大，路由器越愿意为缓存亲和接受额外排队。不要只比较命中率；同时检查平均排队和 P95 端到端延迟。

## 模拟器没有覆盖什么

实验故意省略了以下生产因素：

- 每个副本一次只串行处理一个请求，不模拟连续批处理。
- 前缀使用精确标签，不进行词元级相似度计算。
- 缓存没有容量上限、分块、驱逐或跨副本传输。
- 就绪状态只在请求到达时判断；已经接收的工作不会被故障中断。
- 没有网络开销、指标延迟、自动扩缩容、重试和预填充/解码分离。
- `service_ms` 与缓存节省值由输入给定，不来自模型或硬件测量。

这些限制是实验结论的边界，也是把实验迁移到真实推理引擎时需要逐项补上的测量内容。

## 验收标准

- 能解释模型级路由与副本级路由的差异。
- 能复现无故障、单副本故障和全副本不可用三组结果。
- 能解释前缀亲和为什么既可能减少重复计算，也可能增加排队。
- 能指出至少四项模拟器没有覆盖的生产因素。
- 能设计一份真实服务实验记录，包含模型、引擎版本、硬件、请求前缀分布、并发、缓存配置、故障时间线及 TTFT、TPOT、错误率和恢复时间。
